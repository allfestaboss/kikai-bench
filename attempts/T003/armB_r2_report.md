## どう読み取ったか（経路）

対象は `corpus/nist/nist_ftc_06_asme1_ap242-e2.stp` の1ファイルのみ（10971行）。
Grep/Bash が使えないので、**Read の offset/limit だけで場所当てをした**。手順:

1. 先頭60行を読み、実体番号が行番号に対して単調増加していること（`#10` が9行目）を確認。
   以降「行番号 ↔ 実体番号」の対応を作り、二分探索的に位置を当てる方針に切り替えた。
2. offset を大きく取って EOF 警告を出させ、総行数 10971 を確定（実行ではなく Read の警告文から）。
3. 数点をピンポイント（limit=3〜4）で読んで、行番号と実体番号の対応表を作成。
   line 3000=#2204 / 4200=#3308 / 5000=#4108 / 6000=#5108 / 7000=#6108 / 8000=#7108 /
   9000=#8108 / 10500=#9608。差分が 892 で一定になる帯（4200行以降）は
   「1行1実体で複合実体が無い＝B-rep幾何」と判断し、読み飛ばし対象にした。
4. 末尾（10600-10971）を読んで単位系と検算用のカウンタを取得。ここで
   `#9948=INTEGER_REPRESENTATION_ITEM('number of geometric tolerances',28.)`,
   `('number of composite tolerances',4.)`, `('number of datums',6.)`,
   `('number of datum targets',6.)` を得た。**以降これを答案の検算に使った。**
5. 意味的PMIの本体は先頭寄り（#65〜#348）にあった。行 60-1018 を通しで読んで
   公差実体・データム・データムシステム・公差域を全部拾った。
6. 行 1019-1458 を読み、`DESCRIPTIVE_REPRESENTATION_ITEM('datum references', ...)`
   28件を**独立した検算**として使った（後述）。
7. 残りの帯（1459-3010 / 3004-3610 / 10020-10600）は下請け2体に Read だけで走査させ、
   意味的PMI実体が1件も無いことを確認した。

### 単位換算
ファイル内の `#10033=(CONVERSION_BASED_UNIT('inch',#9962) ...)`、
`#9962=LENGTH_MEASURE_WITH_UNIT(LENGTH_MEASURE(25.4),#9960)`、`#9960` は SI ミリメートル。
よって **換算係数 25.4 はファイル内から取得**しており、外部知識は使っていない。
全28件の公差値の単位は `#10033`（inch）だった。

## 判断に迷った箇所

1. **データム記号の一覧を「6」にするか「10」にするか。**
   ファイル内カウンタは `number of datums = 6` だが、`DATUM` 実体は #288-#297 の10個ある
   （ID_ATTRIBUTE の 'datum.1'〜'datum.10' でも10個と裏が取れた）。
   6 は DATUM_FEATURE（#140-#145）の数で、残る G/H/J/K は
   PLACED_DATUM_TARGET_FEATURE（#71-#76）側から定義されているデータムだった。
   設問は「ファイルに**定義されている**データム記号を全て」なので、
   **DATUM 実体の identification を全部（A,B,C,D,E,F,G,H,J,K の10個）** で出した。
   記入例も 9個/6個と数が揃っておらず「datum_feature の数」ではないので、この解釈を採った。
   ※ I を飛ばして J,K になっているのは規格通り（誤読ではない）。

2. **公差値の丸め。** 値は `0.0250000000001` のように mm→inch 換算由来の誤差を含む。
   規則「ファイルに実際に入っているもの」に従い **value は生値のまま**、
   value_mm は `生値 × 25.4` をフル桁で書いた（0.635 等に丸めていない）。
   採点が丸め値を期待している場合でも許容誤差内に入るはず。

3. **公差の種別（葉の型）。** 複合実体は `POSITION_TOLERANCE` /
   `SURFACE_PROFILE_TOLERANCE` を葉として採用。#107/#108 は単一行の
   `PERPENDICULARITY_TOLERANCE(...)`、#146-#148 は `FLATNESS_TOLERANCE(...)` で、
   これらは葉の型がそのまま実体名。

4. **複合公差の upper/lower。** `GEOMETRIC_TOLERANCE_RELATIONSHIP('composite','',#337,#338)`
   の第1引数側（値が大きい方）を upper、第2引数側（小さい方）を lower とした。
   記入例（486=1.2 が upper、487=0.2 が lower）と同じ向き。

## 課題文が決めていないと思った箇所

1. **データム記号の並び順。** `datums`（ファイル全体の一覧）をどの順で出すかが
   課題文にも規則にも書かれていない。記入例が A,B,C,... のアルファベット順だったので
   **アルファベット順**に決めた。ファイル内の DATUM 実体の出現順は D,B,C,A,E,F,H,G,J,K で
   これとは違う。

2. **「データム記号」に datum target 由来のデータムを含むか。** 上の「迷った箇所1」と同じ。
   課題文は区別していない。含める側に決めた。

3. **公差域の形（zone_form）が付かない公差の表現。** TOLERANCE_ZONE を持たない公差が多数ある。
   記入例が空文字 `""` を使っていたのでそれに合わせた（null ではなく ""）。

4. **`unit` フィールドの表記。** 記入例は `"millimetre"` / `"inch"` の2種。
   このファイルの CONVERSION_BASED_UNIT の名前は `'inch'` なのでそのまま `"inch"` とした。
   （もう一つの `#10032` は `'MILLIMETRE'` と大文字だが、公差値はどれもこれを参照していない。）

## 課題・記入例の側の欠陥だと思ったところ

1. **記入例に「値の丸め」の方針が無い。** 記入例の2ファイルはたまたま値が
   0.005 / 0.8 / 0.2 のようにきれいで、`value` を生値で書くのか丸めるのかが判別できない。
   本課題の対象ファイルは値が `0.0250000000001` のように必ず誤差を含むので、
   ここは記入例からは決められない。今回の欠陥の直し（記入例の作り直し）では
   この点は埋まっていない。

2. **`datums` 一覧の定義が曖昧なまま。** note に「一覧（datums）は省略していない」と
   書かれたが、**何を数えたら一覧になるのか**（DATUM 実体か、DATUM_FEATURE か）は
   依然として書かれていない。記入例の stc_10 が9個・ctc_03 が6個というだけでは、
   datum target 由来のデータムを含むかどうかが決まらない。T001 の欠陥(2)は
   「短かった」ことより「何の一覧かを言っていない」ことが本体ではないかと思う。

3. **`id` フィールドの意味が明示されていない。** 記入例から STEP の実体番号だと
   推測できるが、課題文には書かれていない。`composite_partner` が実体番号だと分かるのも
   記入例からの推測。

4. **`asked` に無いフィールドが `answer_format` にある。** `zone_form` /
   `projected_length_mm` / `unit_length_mm` / `unit_area_shape` /
   `composite_role` / `composite_partner` は `asked` の5問のどれにも対応していない。
   note によればこれが T001 の欠陥(3)の対象で、今回は記入例に載せて可視化した、
   ということだと理解した。ただし**課題文（asked）の側は直っていない**ので、
   「訊かれていないことを答えている」構図そのものは残っている。

## ファイルの内部矛盾に気づいた点

1. **`number of datums = 6` と DATUM 実体10個の不一致**（上述）。ファイル自身の
   検証プロパティと実体数が食い違う。矛盾というより「6 は datum feature の数」という
   別勘定だと解釈したが、ファイルだけ見ると読み手を誤らせる。

2. **TOLERANCE_ZONE が9個しかない。** 位置度は11件（#111-#114, #133-#139）あるのに
   TOLERANCE_ZONE（#124-#132）は9個で、**#138 (Position.9) と #139 (Position.8) だけ
   公差域の形が定義されていない。** この2件は表示側では 'position' の注記があり
   データム参照も D,C,J / D,C,K と入っているので、意味側の取りこぼしに見える。
   答案では zone_form を `""` にした（推測で 'cylindrical or circular' を補わなかった）。

3. **`#348` の名前が `Geometrical Tolerance.1`** で、他の面輪郭度が
   `Position surfacic profile.N` なのに対し命名が揃っていない。中身は
   SURFACE_PROFILE_TOLERANCE でデータムは A,B,C。名前から種別を推測すると外す作り。
