# T001 を n=3 で測り直した記録

2026-08-10。論文（[10.5281/zenodo.21862231](https://doi.org/10.5281/zenodo.21862231)）
§4.4 に未解決として残した「反復が2業種しかない」を閉じるための測定。
**課題も参照解も一切変えていない。**同じ課題を armB・armC で3回ずつ、計6回走らせただけである。

kikai を選んだ理由は、答えが完全に離散だからである。公差の件数・種別・データム記号・
修飾子はどれも実数値ではないので、**厳密一致に意味がある。**kanzei（分類コード）と
zeimu（集合）はそうで、jiban（実数ベクトル）はそうでない。3業種目としてここに揃う。

隔離は `big-business/.runs/kikai-T001-n3/<arm>_run<n>/` に置いた。共有スクラッチパッドの
**外**である。kanzei の n=5 では前回の解答が各 run から到達できる位置にあり、
「25%が毎回ちがう」が下限になった。今回は走らせる前に参照解への到達経路が 0 であることを
確認している。下請けエージェントは明示的に禁止した（kanzei ではばらつきに内部並列度が乗った）。

## 何が言えるか

**点数が並んだので、腕の差はコストにしか出ていない。**armC が armB の 1/1.49 のトークンで
同じ答えに到達している。差 41,672 トークンはプールSD（2,998）の **13.9倍**で、
3本ずつのレンジは重ならない（armB 123,070–128,436、armC 81,122–87,246）。

向きに注意が要る。armC は**トークンでは安いが、時間では 1.56 倍かかっている**（402秒 対 258秒）。
コード実行はモデルに読ませる代わりに機械に読ませるので、文脈に載る量が減る一方、
書いて走らせて直す往復が増える。ツール使用回数（25.3 対 13.3）がその往復である。
**「安い」は単位を書かないと意味が反転する。**

## 見つかった出題側の欠陥

**Q5 で採点される5つのフィールドが、課題文にも解答形式にも一度も現れない。**

| フィールド | 採点 | task.json 内の出現 |
|---|---|---|
| `modifiers` | Q5 | 1回（解答形式の例にある） |
| `zone_form` | Q5 | **0回** |
| `projected_length` | Q5 | **0回** |
| `unit_length` / `unit_length2` | Q5 | **0回** |
| `unit_area_shape` | Q5 | **0回** |

課題文の側にも「公差域」「突出」「単位あたり」「直径」「円筒」「球」のいずれも出てこない。
なお `projected_length` `unit_length` `unit_area_shape` はこのファイルに対象が1件も無いので
（敵対テストでも該当なしとして飛ばされる）、**実際に減点したのは `zone_form` だけ**である。
解答形式の記入例が `Flatness.1` を使っているのが効いていて、**平面度には直径記号が付かないので、
例は `zone_form` の存在を構造的に隠している。**

結果、**6本全部が同じ9件で同じように外した。**位置度8件の `cylindrical or circular` と
1件の `spherical` を、6本とも `null` で出している。腕も手法も独立で、armB は STEP を直読し
armC はパーサを書いたのに、外し方が1件ずれもなく同一である。読解の失敗ではない。
**聞かれていないことに答えなかっただけである。**

**敵対テストは、この答案を既に「攻撃」として作っていた。**
`checker/adversarial.py` の `evil_drop_zone_form` は、参照解から `zone_form` を空にして
採点器が気づくかを試すケースである。その得点は **94.6/100・Q5 で失点**——
6本の解答者が受け取った点数・失点箇所と、完全に同じである。
このケースは合格として記録されている。採点器がちゃんと気づいたからである。

機構は設計どおりに動いた。このフィールドが採点対象であることを知っていて、
落とせば減点されることを証明した。知りようがなかったのは、
**課題文がそのフィールドを一度も要求していない**ということだけである。
減点された答案のほうが、課題文に忠実だった。

これは §3.1.1 の構造を一段はっきりさせる。採点器・較正・敵対テストは
すべて参照解の関数なので、参照解の**中**の誤りを検出できない。
だが**課題文は参照解の関数ではない。**ベンチマークの中で唯一、参照解と独立に書かれる。
同じ理屈で、3つの検査は参照解と課題文の**あいだ**の食い違いも検出できない。
内部整合性が小数点以下まで完璧なまま、聞いていない問いの答えを採点し続けられる。

この欠陥は、論文が数えた15件とは**見つかり方が違う。**14件は被験者が「おかしい」と書いてきた。
これは誰も書いてこなかった。書きようがない —— 存在を知らされていないフィールドの欠落は、
**答案を採点して初めて見える。**被験者からの報告を欠陥発見の主経路として数えると、
この種類は構造的に取りこぼす。

## 参照解が「外部の検算値」と食い違う件

NIST はこのテストファイル自身に検証プロパティを埋めている。

```
#9948 number of geometric tolerances = 28
#9949 number of composite tolerances = 4
#9950 number of datums          = 6
#9951 number of datum targets   = 6
#9952 number of semantic pmi elements = 67
```

データ提供者が期待値をデータに書いているので、参照解を作った人の外側から検算できる。
これは §3.1 の閉ループに対する部分的な解になっている。**ところが解決しきっていない。**

`number of datums = 6` は `DATUM` 実体の数（10）と合わない。NIST は `DATUM_FEATURE` 由来の
A–F だけを数え、`PLACED_DATUM_TARGET_FEATURE` 由来の G・H・J・K を
`number of datum targets` の側に計上している。本参照解は `DATUM` 実体で数えて 10 としている。
**どちらも正しい。**「データムの数」という語が2つの量を指しているだけである。

6本中5本が独立にこの食い違いを指摘し、うち3本は「参照解が 6 を採っていると衝突するので、
採点前に定義を確認したほうがよい」と書いてきた。

**外部の権威が検算値を与えても、正解は確定しない。曖昧さが「その数が何を数えているか」へ
移動する。**検算値の一致は、定義が一致していることの証明ではない。

## 直していないこと

**この測定では課題を直していない。**直せば、直す前後で測ったコストが比較できなくなる。
欠陥は6本すべてに等しくかかっているので、腕どうしの比較（この測定の目的）は汚れていない。
`zone_form` を解答形式に足すのは別の版でやる。
