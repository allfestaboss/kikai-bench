# kikai-bench — AIは機械図面の幾何公差をどこまで読めるか

[![DOI](https://zenodo.org/badge/DOI/10.5281/zenodo.21847247.svg)](https://doi.org/10.5281/zenodo.21847247)
[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](LICENSE)

STEP AP242 に埋め込まれた **semantic PMI（機械可読な幾何公差・データム）** を
読み取る能力を、機械採点で測るベンチマーク。
cad-bench / sekisan-bench / doboku-bench /
kanzei-bench / jiban-bench に続く AI実務到達度インデックスの6本目で、
**CAD横断シリーズの3業界目**（建築2D → 土木SXF → 機械STEP）。

## 測るのは「書けるか」ではなく「読めるか」

doboku-bench は SXF を**書けるか**を測った。こちらは**読めるか**を測る。

幾何公差を読み違えることは実務の事故に直結する。`⌖ ⌀.025 Ⓜ | C | A | B` の
データムの順序を入れ替えれば、測定の基準面が変わり、合否が変わる。
そして semantic PMI は正解が構造化されているので、採点が素直に作れる。

## 制度的な空席 — 業界が自分で書いている

土木では国交省が「電子納品チェックシステムでは成果品の内容を確認することはできません」と
自ら明記していた。機械はもっと直接的だった。

JAMA/JAPIA が2023年4月に参加各社（トヨタ・ホンダ・マツダ・スズキ・ダイハツ・いすゞ・
SUBARU・三菱・スタンレー電気ほか）へ行った課題ヒヤリングの結果、**第1位がこれである**。

```
   各社から提出された課題              課題への対応
1  効率的な検図方法が不明            (本書でのモデル作成の取組みとは、別に対応)
2  2D図面と比較すると、3D図面作成工数が増加   モデル作成工数課題を考慮したモデルを検討
```

（日本自動車工業会「3D図面お手本データの解説」2024-03-31, p.8）

**業界自身が「検図の方法が分からない」を筆頭に挙げ、標準化の取り組みからは棚上げしている。**

2009年の「3D単独図CAD機能検証結果レポート」を見ると、工程はこうなっている。

```
3Dモデル作成 → 3D単独図モデル作成 → 検図（紙出力）・承認
検証項目のひとつ：「3D単独図を三角法で2D展開して検図を行えるか」
```

**データには機械可読な幾何公差が入っているのに、検図は紙に出して人が見ている。
しかもその方法が2023年時点でまだ定まっていない。**

3業界を同じ物差しで測ると、「検査されていない」にも段階があることが見える。

| 業界 | 空席の形 |
|---|---|
| 建築2D | 検図はあるが基準の適用が属人的（証拠は弱い） |
| 土木 | **検査する仕組みはあるが、中身を見ない** |
| 機械・製造 | **データは機械可読なのに、検査方法が決まっていない** |

## 参照解は NIST が持っている

| | 出どころ | 誰が確定させたか |
|---|---|---|
| 入力 | NIST / MBx-IF のテストケース（FTC・STC・CTC） | 米国 NIST |
| 形式 | ISO 10303-21 / -242（AP242） | ISO |
| 基準 | ASME Y14.5 | ASME |
| 参照解 | STEP ファイルに実際に入っている semantic PMI | **こちらは何も決めていない** |

利用条件は原文で `The test cases, CAD models, and STEP files can be used without any restrictions.`。
**corpus をそのまま同梱できる**ので、検証可能性が保てる。

日本側の JAMA お手本データは幾何公差の解説まで付く優れた資料だが、
**再配布が明示的に禁止**されているため採用しなかった（[docs/SOURCES.md](docs/SOURCES.md)）。
同じ「業界標準化のための供試データ」で、日米で出し方が逆になっている。

## 較正 — 生テキストの手読みと一致

`bench/selfcheck.py` は step.py も pmi.py も呼ばず、ファイルから直接読んだ行を
リテラルに書き下して突き合わせる。

```
$ python -m bench.selfcheck
--- #146 Flatness.1 ---
  kind       手=FLATNESS_TOLERANCE    抽出=FLATNESS_TOLERANCE
  value_mm   手=0.254000000001        抽出=0.254000000001        差=0.00e+00
--- #111 Position.21 ---
  datums     手=('C', 'A', 'B')       抽出=('C', 'A', 'B')
  value_mm   手=0.635000000003        抽出=0.635000000003        差=0.00e+00
  modifiers  手=('MAXIMUM_MATERIAL_REQUIREMENT',)  抽出=('MAXIMUM_MATERIAL_REQUIREMENT',)

較正: OK（手読みと一致）
```

単純実体（FLATNESS）と、データム参照＋MMC修飾子つきの複合実体（POSITION）の両方で一致する。

## 外部検算 — 採点器を作る前に、抽出器のバグを5件見つけた

`bench/crosscheck.py` が `NIST-FTC-PMI-Definitions.xlsx` と突き合わせる。
較正（`selfcheck.py`）は自分の手読みとの照合なので、同じ思い込みをしていれば一緒に間違える。
こちらは照合先が外部なので、その思い込みごと検査できる。

**jiban-bench では採点器と敵対テストを作り込んだ後に、腕が参照解の誤りを4件見つけた。**
今回は外部の照合先が最初からあるので、作り込む前に使った。結果、5件出た。

| # | 見つかった抜け | 影響 |
|---|---|---|
| 1 | 公差域の形（`TOLERANCE_ZONE_FORM`）を一切拾っていない | `⌀`（円筒）と `S⌀`（球）の区別が消える |
| 2 | 複合 `SI_UNIT` のパートは `(prefix, name)` なのに `[1],[2]` を見ていた | **mm 換算が1000倍狂う**（FTC-09/10） |
| 3 | magnitude が複合実体の形を扱えていない | FTC-08/11 の公差値が丸ごと `None` |
| 4 | 共通データムが `DATUM_REFERENCE_ELEMENT` を1段はさむ形に未対応 | `E-F` が `#437-#436` になる |
| 5 | **単純形の第5引数にあるデータム参照を見ていない** | **361件中48件（13%）のデータムが消える** |
| 6 | 突出公差域（`PROJECTED_ZONE_DEFINITION`）を拾っていない | `Ⓟ` が丸ごと落ちる。corpus に23件 |
| 7 | 複合公差（`GEOMETRIC_TOLERANCE_RELATIONSHIP`）を拾っていない | 上下2段の記入枠が別々の公差に見える。corpus に42対 |
| 8 | **DATAセクションの最後の実体を落としていた** | **全ファイルで末尾1件が黙って消える** |

一致率は 32/45 → 36/45 → 39/45 → **40/45** と上がった。

**8 が最も深刻だった。** 実体を切り出す正規表現の先読みを
`(?=#\d+\s*=|ENDSEC)` としていたが、走査対象は `ENDSEC` の手前で切っている。
末尾には次の `#id=` も `ENDSEC` も来ないので、**全ファイルで最後の1実体が
黙って消えていた**。`nist_stc_07` は最後の実体が幾何公差だったため、
宣言22件に対し21件しか取れず、しかも複合公差の関係がその実体を指していたので
「参照切れのある壊れたファイル」だと誤って結論していた。**壊れていたのはこちらだった。**

見つけたのは腕（armC）である。「参照切れは1件も無い」「stc_07 は22件」と
こちらの結論を否定してきたので確かめたところ、向こうが正しかった。

2 と 5 は静かに壊れる種類のバグである。値も種別も出るので、
一見それらしい参照解ができあがる。**採点器を先に作っていたら、この参照解を真として
敵対テストを全通過させ、「検証済み」と称して公開していた。**

較正が素通りした理由もはっきりしている。手読みしたのが FTC-06 だけで、
その公差がたまたま全て複合形・inch 系だった。**較正は形式の違う複数ファイルで取る**
必要がある。いまは3形式5ケースで取っている。

### 残っている5件は、こちらのバグではなくモデル側の差

一件ずつ実データで確かめた。

| ATC | 定義が求めるもの | モデルの実際 |
|---|---|---|
| 80 ×2 | `⌀.025 \| D \| B \| C`（円筒） | `D\|B\|C` の .025 は**球形**しか無い。円筒のものは `A\|B\|C`（+MMC） |
| 82 ×2 | `.020` と `.060` を `A\|G\|H` で | .020 も .060 もファイルに在るが、`A\|G\|H` を参照するのは **.01 と .03 だけ** |
| 86 | `⌀1.5 \| A \| B \| C` | FTC-10 の位置度は `0.0/0.5/0.65/0.75/0.8/1.0/1.2` で **1.5 が無い** |

NIST 自身が「CAD がどうモデル化したか／どう STEP に書き出したかで差が出うる」と
断っている。**差があること自体を記録する**のが正しい扱いで、これは失点ではない。

むしろ読解ベンチとしては、**定義と実装が食い違う実物**が手元にあるのは価値がある。
「図面にこう書いてあるはず」と「モデルに実際こう入っている」を区別できるかを
問う課題が作れる。

未解釈が1件（FTC-11 ATC55 `⌢ (197.9)`）。公差値を持たない線の輪郭度で、
公差記入枠として読めない。**黙って捨てず、未解釈として数え上げている。**

## 実物から確定させた構文

仕様書からの推測では書いていない。実データで出てきた形だけを実装した。

```
単純     #146=FLATNESS_TOLERANCE('Flatness.1','',#9981,#2605);

複合     #111=(GEOMETRIC_TOLERANCE('Position.21','',#9987,#977)
               GEOMETRIC_TOLERANCE_WITH_DATUM_REFERENCE((#329))
               GEOMETRIC_TOLERANCE_WITH_MODIFIERS((.MAXIMUM_MATERIAL_REQUIREMENT.))
               POSITION_TOLERANCE());

公差値   #9981=LENGTH_MEASURE_WITH_UNIT(LENGTH_MEASURE(0.01000000000004),#10033);
         #10033=(CONVERSION_BASED_UNIT('inch',#9962,…)…);
         #9962=LENGTH_MEASURE_WITH_UNIT(LENGTH_MEASURE(25.4),#9960);

データム #329=DATUM_SYSTEM('Datum System .5',$,#9395,.F.,(#308,#309,#310));
         #308=DATUM_REFERENCE_COMPARTMENT('',$,#9395,.F.,#290,$);
         #290=DATUM('',$,#9395,.F.,'C');
```

区画の並び順がそのままデータムの優先順位になる。

**共通データム**は着手時に想定していなかった形で、FTC-08 で出てきた。
`COMMON_DATUM_LIST((#76,#77))` は2つのデータムが1つの区画として働くもので、
ASME Y14.5 では `A-B` と書く。**推測で潰さず、実物に合わせて対応した。**

## 腕の試走 — 採点器を作る前に分離を確かめた

B（コード禁止）と C（Python可）に同じ構造知識を渡し、10,970行 / 1.9MB の
ファイルから28件を拾わせた。差が出るとすればコード実行の有無だけになる。

| 腕 | 結果 | トークン | 所要 |
|---|---|---|---|
| armB 知識のみ・コード禁止 | 28/28 完全一致 | **179,004** | 5分31秒 |
| armC 知識+Python | 28/28 完全一致 | **77,585** | 6分00秒 |

**正答では分離しなかった。** 種別・値・mm換算・データムの順序・公差域の形まで
28件すべてが参照解と一致し、データム記号10個も一致。jiban-bench と同じ形である。

分離したのはコスト。**armB は armC の 2.3倍のトークンを使っている。**
一方で所要時間は armB のほうが短い（5:31 対 6:00）。armC はパーサを書いて
デバッグする時間を使っており、**トークンでは勝ち、時計では負けている**。
仕事量が1ファイルだと、コード実行の初期費用が回収しきれていない。

→ 課題を重くするなら「ファイル数を増やす」方向が効く。corpus には
AP242 が17ファイルある。1ファイルで 2.3倍なら、17ファイルでは開くはず。

### 腕が、こちらの見落としを2つ見つけた

**1. ファイル自身が検証プロパティを持っている。**

```
#9948=INTEGER_REPRESENTATION_ITEM('number of geometric tolerances',28.);
#689=DESCRIPTIVE_REPRESENTATION_ITEM('datum references','D,B,C');
```

書き出した側が数え上げた値がファイルに埋まっている。**xlsx の定義（45件）より
照合先として強く、corpus のほぼ全ファイルを覆う。** こちらは10,970行を
読み通しておらず気づいていなかった。`bench/crosscheck.py` に組み込んだ。

その結果、**2ファイルで宣言と中身が食い違う**ことが分かった。

```
nist_stc_07_asme1_ap242-e3.stp   宣言22 / 抽出21  （差 -1）
nist_stc_10_asme1_ap242-e2.stp   宣言34 / 抽出37  （差 +3）
```

実体を数え直したところ抽出値と一致し、未対応の公差型も無かったので、
**こちらの誤りではなく宣言側が中身と合っていない**。どちらも2023年の STC 系である。

**2. 複合公差（composite FCF）を拾っていない。**

```
#284=GEOMETRIC_TOLERANCE_RELATIONSHIP('composite','',#337,#338);
```

上段（0.05, D|B|C）と下段（0.01, D）が対で1つの公差記入枠を成す。
輪郭度の名前が重複して見えるのはこのため。corpus の11ファイルに存在する。
**未対応。次に塞ぐ。**

## T002 で分離した

6ファイル・202,823行・公差157件（T001 比で行数18.5倍）。

| 腕 | 完遂 | 提出した公差 | 正答 | トークン | 所要 |
|---|---|---|---|---|---|
| armB コード禁止 | **5/6ファイル** | 153 | **153/153** | **1,053,066** | 44分47秒 |
| armC Python可 | **6/6ファイル** | 157 | **157/157** | 216,591 | 23分43秒 |

armB のトークンには下請けエージェント **551,489** を含む。内訳は本体 501,577 +
下請け 551,489。この下請けが何をしていたかは次項。

**手を付けた範囲は両方とも全問正解。** 差が出たのは「どこまで行けたか」である。
armB は armC の 2.3倍のトークンと 1.4倍の時間を使って、**最後の1ファイルに届かなかった**。
残ったのが最小のファイル（公差4件）だったのが、力尽き方をよく表している。

T001（1ファイル）では正答も所要時間も分離せず、トークンだけ2.3倍だった。
ファイル数を6倍にすると、**同じ2.3倍が「完遂できるかどうか」に変わった**。
コード実行が買っているのは正確さではなく到達範囲である。

### こちらのバグが、腕の予算を半分持っていった

armB は「stc_07 に参照切れがある」という問いを下請けエージェントに投げ、
そちらが **551,489トークン・12分17秒**をかけて、`GEOMETRIC_ITEM_SPECIFIC_USAGE`
323件、`DRAUGHTING_MODEL_ITEM_ASSOCIATION` 255件、`SHAPE_ASPECT_RELATIONSHIP`、
`CLOSED_SHELL` の304面を全て突き合わせ、**「参照切れは1件も無い」**と結論した。

正しい。**その参照切れは、こちらのパーサが末尾実体を落としていたことが生んだ幻だった。**

下請けの最後の一文がこの件の要点を突いている。

> `anomalies[0]` should keep stating that no dangling reference was found
> rather than naming a fabricated id.

**参照解の誤りは、点数を狂わせるだけでは済まない。腕の予算を幻の追跡に燃やす。**
armB のトークンの半分以上がこれに消えた。採点器を作る前に参照解を固める理由が、
コストの数字としても出た形になる。

### 提出物そのものも壊れた

armB の `answer.json` は **JSON として不正**だった（オブジェクト間のカンマ落ち）。
手書きで6万字級の JSON を書くと、内容が正しくても器が壊れる。
ただし末尾に `"_incomplete": "ftc_11 はまだ入っていない"` と自己申告しており、
**黙って埋めることはしなかった**。採点上は不正 JSON として扱うべきだが、
今回は分離の測定が目的なのでカンマを補って中身を数えた。

### 採点器を書くときの注意（この計測で踏んだ）

`value_mm or -1` と書いたせいで、**公差値 0.0 が falsy に潰れて不一致になった**。
該当は `⌖ ⌀0Ⓜ`（最大実体公差方式のゼロ位置度）という正当な指定で、
両腕とも正しかったのにこちらが誤判定していた。**ゼロは有効な公差値である。**

## 採点

`./run.sh` が (1)較正 → (2)外部検算 → (3)敵対テスト → (4)採点 の順で走る。
どれか落ちたら数字を出さない。

```
提出             網羅     種別    値/mm データム 修飾子等     複合      合計      %      tok      時間   tok/件   倍率
参照解          20/20    15/15    20/20    20/20    15/15    10/10  100.0/100 100.0%        -         -        -      -
_armB.repaired  17/20    15/15    19/20    19/20    15/15    10/10   94.9/100  94.9%        -         -        -      -
armB                -        -        -        -        -        -    0.0/100   0.0%    1053k  44分47秒     6707   4.9×  ★失格
armC            20/20    15/15    20/20    20/20    15/15    10/10  100.0/100 100.0%     217k  23分43秒     1380   1.0×
```

**armB は失格（0点）。** 提出した `answer.json` が JSON として壊れていた。
中身は 153/153 正解だったが、器が壊れていれば受け取れない。
カンマを補った `_armB.repaired` なら 94.9点で、失点は未提出の1ファイル分だけ。
**「読める形で出せたか」と「中身が合っていたか」は別の軸である。**

### 採点器の設計に入れた、実際に踏んだ罠

| 罠 | 対処 |
|---|---|
| **ゼロは有効な公差値** | `value or -1` で `⌀0Ⓜ` が不一致に化けた。falsy 既定値を禁じ、`num()` で明示的に None 判定 |
| 手書きの答案は器が壊れる | 不正 JSON は失格。armB の実例がある |
| 部分提出は実際に出る | 未提出ファイルはその分を0点にし、提出済みは正しく採点 |
| データムは順序が優先順位 | 集合ではなく列で比較 |
| 取りこぼしと捏造は対称 | Q1 は F1。20件しか読めない答案と8件でっち上げた答案を同点にしない |
| **課題が訊いていないものを減点しない** | `grade_levels` で課題ごとに採点水準を選ぶ。T001 は複合公差を設問に含めていないので Q6 を外す |
| 列挙値の書式差 | `.FREE_STATE.` と `FREE_STATE` は読み取り能力の差ではない。採点器で正規化 |

### 参照解自身が規則を破っていた

採点したら両腕が同じ箇所で落ちたので調べたところ、**こちらの参照解が
`PROJECTED_TOLERANCE_ZONE` を修飾子に合成していた**。ファイルの
`GEOMETRIC_TOLERANCE_WITH_MODIFIERS` にその列挙値は無く、記入枠の Ⓟ に
合わせて足したものだった。

課題規則には「**ファイルに実際に入っている semantic PMI を報告せよ**」と
書いてある。腕はそれに従い、参照解が破っていた。合成をやめ、突出長さの欄だけで
表すようにした。**腕が揃ってこちらと食い違うときは、こちらを疑う。**

### 敵対テスト

T001 10/10、T002 13/13。実際に踏んだ失敗をそのままケースにしてある
（ゼロを null にする / カンマ落ち / 公差の捏造 / データムの順序反転 /
mm 換算忘れ / 公差域の形を落とす / 突出長さを落とす / 複合公差の対を落とす）。

課題が採点しない水準や、対象が存在しない変異は自動で飛ばす。
**効かない変異を「捕まえられなかった」と誤認しないため。**

## 抱えていた抜けを全部塞いだ

腕や検算が挙げてきた4件。**塞いだ結果、検証プロパティとの一致が 9/10 → 10/10 になった。**

### 単位あたりの公差

```
#14257=( FLATNESS_TOLERANCE()
         GEOMETRIC_TOLERANCE('Flatness.1','',#14256,#14252)
         GEOMETRIC_TOLERANCE_WITH_DEFINED_AREA_UNIT(.CIRCULAR.,$)
         GEOMETRIC_TOLERANCE_WITH_DEFINED_UNIT(#14255) );
```

記入枠では `▱ .01 / Ø1.00`。「面全体で0.01」ではなく「**Ø1.00インチの範囲につき0.01**」。
落とすと規制の強さがまったく変わる。実物では3形態が出た。

| ファイル | 公差 | 単位 |
|---|---|---|
| ctc_03 | 平面度 0.005in | **矩形** 0.25 × 0.25 in |
| ftc_07 / stc_07 | 平面度 0.01in | **円形** Ø1.00 in |
| ftc_10 / stc_10 | 真直度 0.2mm | **長さ** 15 mm（面積指定なし） |

### `nist_stc_10` の宣言34 vs 抽出37 — 数え方の規約が違った

このファイルは**検証プロパティの組自体が他と違う**。

```
stc_10:  annotations / datum features / dimensional locations / geometric tolerances / views
ftc_06:  annotations / composite tolerances / datums / datum targets / dimensional locations
         / dimensional sizes / geometric tolerances / semantic pmi elements / views …
ftc_10:  （検証プロパティ自体が無い）
```

stc_10 だけ **`number of composite tolerances` を宣言せず**、代わりに `datum features` を使う。
**複合公差の上下2段を1件と数える別の生成器**の出力である。`37 − 複合3対 = 34` で合う。

検算器にこの規約差を持たせた。「複合の宣言が無いファイルは畳んだ数と比べる」。
**規約を推測で決めず、宣言の組から読み取っている。**

### stc_07 の2件 — 抽出には影響しないが、報告する

- `#14028` / `#14030` の `DIMENSIONAL_SIZE_WITH_DATUM_FEATURE` が**自分自身を参照**している。
  幾何公差の抽出経路には乗らない（データムは `DATUM` 実体を直接読んでいる）
- 同一の公差域に `PROJECTED_ZONE_DEFINITION` が重複（#16658 に2件、#16799 に4件）。
  **値は全て同じ**なので結果は変わらない

どちらも結果に影響しないが、**課題が「ファイルの内部矛盾に気づいたら報告せよ」と
訊いている以上、参照解が黙っていてはいけない。** `anomalies` として出すようにした。
突出公差域の重複も、**値が異なれば黙って1つ選ぶことになる**ので、その場合は報告する
（このcorpusでは同値だった）。

## 記入例が3通りに壊れていた

シリーズの別のベンチ（bim-bench）で、課題文の説明文に設問の答えを印字したまま
腕を走らせる事故を起こした。腕の3走すべてが独立に申告して分かった。
較正も外部検算も敵対テストも参照解の関数なので、**原理的に課題文を見ていない。**
同じ検査をここに当てたら、**解答様式の記入例が3通りに壊れていた。**

`python3 -m bench.leak` で数えられる。

| | T001 | T002 |
|---|---|---|
| **漏れ** 記入例の行が採点対象の行そのもの | **1件** | 0件 |
| **誤り** 記入例の値が参照解と食い違う | **1件** | **2件** |
| **隠蔽** 採点対象なのに例に一度も出ないフィールド | **6件** | **11件** |

### 漏れ — 記入例は作り話ではなく、本物の答えだった

```
{"id": 146, "kind": "FLATNESS_TOLERANCE", "name": "Flatness.1",
 "value": 0.01, "unit": "inch", "value_mm": 0.254, "datums": [], "modifiers": []}
```

**8フィールドすべてが参照解と一致する。**28件の公差のうち1件を配っていた。

### 誤り — 一覧が実物より短い。省略とは書いていない

```
T001  記入例 datums ['A','B','C']        実物 ['A','B','C','D','E','F','G','H','J','K']
T002  記入例 datums ['A','B']            実物 ['A','B','C','D','E']
T002  記入例 composites [[337,338]]      実物 6組
```

`datums` は採点対象である。**記入例は、そのファイルの答えではない値を形として示している。**
見本の省略なら「省略」と書くべきで、課題文のどこにも書いていない。

### 隠蔽 — これは既に高い代償を払っている

平面度には公差域の形が無いので、記入例に `zone_form` が出ない。
**6本の独立した解答者が、腕も手法も違うのに1件のずれもなく同じ9箇所を null で出した。**
読解の失敗ではなく、聞かれていないことに答えなかっただけである（[docs/T001n3.md](docs/T001n3.md)）。

T002 の記入例は**11フィールド**を隠している。`zone_form` / `projected_length` /
`unit_length` / `unit_area_shape` ——**T001 で問題になったフィールドが全部入っている。**

### 3つは互いに逆を向いている

漏れを避けようとして作り物の例を書けば「実在しない行」になり、
実在の行を選べば漏れになる。**正しい形は「実在するが採点対象ではない行」である。**

bim-bench は逆側の検査を持っている——記入例の行が参照解に**実在するか**を確かめる
（作り話を防ぐため）。**両方が要る。**片方だけだと、もう片方に倒れる。

**記入例は直していない。**走行後に直すと、答案を見てから課題文を書き換えたことになる
（同じ失敗で bim-bench の T004 は撤回になった）。**T003 で作り直した。**

## T003 — 記入例を作り直したら、揃っていた失点が消えた

設問・規則・対象ファイル・参照解は T001 と**一字一句同じ**（参照解の同一性は機械照合で確認）。
違いは**記入例だけ**である。記入例は**課題に出てこない2ファイル**から採り、
採点対象のフィールドが全て非空で現れるように選び、一覧も省略していない。

```
T001   94.6 × 6走   ← 6走とも Q5 で 5.4点。同じ9箇所を null
T003  100.0 × 6走   ← zone_form の9箇所が全走で埋まった
```

`python3 -m bench.leak T003` は **漏れ0 / 誤り0 / 隠蔽0。**

### **ただし帰属は確定していない。**原因が3つある

| | 中身 | 評価 |
|---|---|---|
| 1 | 記入例を直した（意図した効果） | armC_r1 が「記入例6行を1文字違わず再現して丸め方と向きを確定させた」と申告。**支持される** |
| 2 | `corpus/` の NIST 定義表 | **こちらの穴。**`NIST-FTC-PMI-Definitions.xlsx` に FTC-06 の値・公差域の形・データム・修飾子が10行ある。armC_r2 が使ったと申告 |
| 3 | note の件数開示 | **こちらが書いた。**「28件中1件」「同じ9箇所」＝公差の総数と `zone_form` 非空の件数 |

**2 は走り終えて事実上外れた。xlsx を読んだのは6走中1走（armC_r2）だけである。**
残る5走は報告で「corpus 配下は対象の .stp 1ファイルのみ」と明記している。
とくに armB_r3 は「`corpus/nist/` を Read で列挙しようとして EISDIR。Bash も Glob も
無いので他にファイルがあるか確認する手段が無い」と報告した——
**armB は構造的に xlsx を発見できない。**その armB が3走とも満点である。

**3 の重さは限定的である。**28 も 9 も**入力ファイル自身が申告している**
（`'number of geometric tolerances', 28.` と ID属性の `tolerance_zone.1〜.9`）。
コーパスから得られない情報ではない。

> **「欠陥を説明する注記が3回連続で答えを漏らした」と一度書いたが、言い過ぎだった。**
> bim T006 の4問の答えは課題文にしか無い情報だった。T003 の2つの件数は入力に埋まっている。
> 漏れであることは変わらないが、程度が違う。**訂正する。**

### 残る本当の問題は `asked` が直っていないこと

armC_r1 と armB_r3 が独立に指摘した。診断は「記入例で隠したから」だったが、
原因はもう1つ **「そもそも `asked` が訊いていない」** があり、T003 はそちらを直していない。
`asked` の5問に対し `answer_format` は15フィールドで、`zone_form` を含む9個はどの設問にも
対応しない。

**したがって「埋まらなければ診断が間違い」という対偶は成立しない。**
埋まっても `asked` は壊れたままである。

清潔な検証には T004 が要る——**note から件数を外し、xlsx を禁止し、`asked` を直したもの。**

### note を見る検査を足した

`bench/leak.py` は記入例しか見ていなかったので、**課題文の散文が採点対象の件数を
漏らしていないか**を見る検査を追加した。ただし**件数が小さいと判定力が無い**
（T002 で件数3と2が本文の「3」「2」に当たり誤検出した）。10未満は要確認と明示し、
本物か誤検出かを人が判定した記録を較正に残してある。

**この検査自身も、課題に無いファイルから例を採ると素通りする欠陥を持っていた。**
例のファイルが参照解に無いと丸ごと飛ばしていた。T003 を作る過程で見つけて直し、
T001/T002 の既知の欠陥が再検出されることを確認している。

## T004 — 設問を採点対象に揃えた。**点数は動かなかった**

T003 は記入例を直したが、**設問は T001 のままだった**——採点される `zone_form` を
`asked` が一度も訊いていない。T004 はそこを揃えた。設問以外は T003 と一字一句同じ。

### 3マス埋まった

| | 記入例が見せる | 見せない |
|---|---|---|
| **`asked` が訊く** | **T004 100.0**（3走×2腕） | **未実施** |
| **訊かない** | **T003 100.0**（3走×2腕） | **T001 94.6**（3走×2腕・全走が同じ9箇所を null） |

> **記入例で見せれば足りる。訊くことは必要ではなかった。**
> T003 と T001 の差は記入例だけで、そこで埋まった。
> T004 と T003 の差は `asked` だけで、点数は動かなかった。

**「訊くだけで足りるか」は言えない。**左下（訊くが見せない）が空いている。

### 「採点されるのに訊いていない」を機械検査にした

T001 の欠陥の一般形である。採点器が見るフィールドの集合と `asked` の語彙を照合する。

```
T001  未問合せ2件（id / zone_form）   ← 6走が揃って同じ9箇所を null にした原因
T002  0件
T003  未問合せ2件（id / zone_form）
T004  **0件**
```

較正・外部検算・敵対テストはすべて参照解の関数なので、この食い違いを原理的に
検出できない。**`asked` を見る検査はここだけである。**

### 向きが逆の不整合は残っている

`label` / `name` / `composite_role` / `composite_partner` は答案様式で必須欄なのに、
`asked` は訊かず採点もしない。**点数には影響しない**が揃っていない（armB_r3 の指摘）。

### **`asked` の「ファイルの単位系は inch」は誤りである**

armC_r2 が指摘し、検算した。

```
大域単位   #10032 = CONVERSION_BASED_UNIT('MILLIMETRE', …)   ← ファイルの単位系は mm
公差値     #10033 = CONVERSION_BASED_UNIT('inch', …)         ← 各公差が個別に参照する側
```

**大域単位を素直に見た腕は「換算不要」と誤読しうる。**走行後なので直さない。

### 同じ形の後退が2件あった

**T002 は正しかった。**`asked` で公差域の形・突出長さ・複合公差まで訊いており、
単位の誤りも持っていない。ところが **T003 を T001 の task.json から派生**させたので、
直っていた `asked` と、無かった単位の誤りを**両方引き戻した。**

> **後継は直近の版から派生させること。**

### 測れる幅の限界（6走中3走が独立に指摘）

Q4 の5項目のうち (3)突出長さ (4)単位あたりの長さ (5)単位あたりの形は
**このファイルに1件も無く、全28件が空**である。`zone_form` も28件中9件。
**実際に差が付くのは修飾子（4件）と公差域の形（9件）だけ。**
設問を揃えても、測れる幅はそこまでである。


### 読めない2行は、独立に再現するツールの性質だった

armB_r1 が9体目の下請けを冗長に立てて同じ区間を再走査させたところ、
**同じ2行（1763・1964）が同じトークン数（81,468 / 253,929）で読めない**と報告した。
`limit=1` にしても読めない。偶発的な失敗ではない。

> **コード実行を許した腕と、Read だけの腕は、同じ入力を見ていない。**

今回は該当行がテセレーションなので無害だが、**設計上の保証ではない。**
corpus を選ぶときに最長行のトークン数を測れば潰せる。

### T003 で開いていた穴は塞いだ

`corpus/nist/NIST-FTC-PMI-Definitions.xlsx` を禁止した。**6走とも「対象の STEP 1本のみ」と申告。**
`FROZEN_T004.json` も禁止に加えた（T003 で1走が開きかけたため）。
